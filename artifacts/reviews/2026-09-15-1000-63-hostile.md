## Change summary

`username_is_valid()` (`auckland-vpn:91-96`) is a pure `case` class match on `[!A-Za-z0-9@._-]`.
It is now called from three ingestion points:

| Site | Location | Message on failure |
|---|---|---|
| config file | `auckland-vpn:129-131` | `VPN_USER contains unsupported characters (allowed: …)` |
| `VPN_USER` env | `auckland-vpn:219-221` | `VPN_USER (from the environment) contains unsupported characters (allowed: …)` |
| `setup` prompt | `auckland-vpn:1034-1036` | `unsupported username '$VPN_USER' (allowed: …); aborted.` |

Downstream sinks are the helper bake `printf 'VPN_USER=%q\n'` (`auckland-vpn:447`) and
`openconnect --user="$VPN_USER"` (`auckland-vpn:664`). The value is only ever assigned at
`auckland-vpn:135` (config), `:218` (env), `:1030` (prompt) — all three validated.

## Q1 — Can an invalid username still reach `--user` or the helper bake? **No.**

- Exhaustive assignment sites: `VPN_USER` is assigned only at `auckland-vpn:135`, `:218`, `:1030`.
  `grep -n 'VPN_USER' auckland-vpn` shows no fourth assignment.
- Both sinks (`:447` bake, `:664` `--user=`) read the same validated variable; `cmd_setup_sudo`
  is gated by `require_vpn_user` (`auckland-vpn:884`), which runs after the top-level validation.
- `:447` additionally uses `%q`, so even a hypothetical bad value could not break out of the baked
  assignment; `:664` passes a single `--user=<value>` argument (no option-injection surface).
- The `start`/`monitor`/`restart` paths re-source the same file, so they inherit the same gate.

**Residual (informational, not a bypass):** a helper installed by a *pre-fix* version keeps its old
baked `VPN_USER` until `setup-sudo` is re-run. The bake is `%q`-quoted and `--user=` is a single
argument, so a stale value is at worst a benign auth failure — no injection.

## Q2 — Quoting / trim / quote-strip smuggling? **No bypass found.**

- Config order is trim (`:117-118`) → quote-strip (`:119-125`) → empty check (`:126`) → class check
  (`:129`). Anything left after one quote pair is stripped is re-validated, so `VPN_USER="alice bob"`
  and `VPN_USER=" alice"` both die (probed).
- Unbalanced quotes die at `:122-124` *before* validation, so a stray quote can never be smuggled
  into the value that reaches the sinks.
- Empirically, `username_is_valid` rejected: space, tab, newline, `; $() | & " ' \\`, DEL, and
  non-ASCII (`é`, CJK). It accepted: `alice`, `student@auckland.ac.nz`, `a-b_c.d`, `-alice`.
  No shell metacharacter passes.
- **Note (defense-in-depth, `auckland-vpn:91-96`):** `username_is_valid ""` returns **0** (valid) —
  the `*[!…]*` case cannot match the empty string. All three call sites guard with a prior
  non-empty check (`:126`, `:219` `-n`, `:1033`), so this is not exploitable today, but a function
  named "is valid" accepting the empty string is a trap for the next caller.

## Q3 — die-context regressions / message drift? **Message drift is real; behaviour is intended.**

- **Drift:** the commit body says the env/setup paths "die with the same message the config loader
  uses". They do not:
  - env inserts `(from the environment)` (not identical);
  - setup is a different sentence entirely (`unsupported username '…'; aborted.`), and it also
    echoes the offending value into the terminal.
  `#63`'s spec asked for the env path to be "rejected with the same message". Tests encode the
  drift (`tests/run-tests.sh:253` asserts `unsupported characters`; `:263` asserts
  `unsupported username`), so any later consolidation must update both.
- **Behaviour change (intended, but worth stating):** `auckland-vpn:218-221` runs unconditionally
  before dispatch (`auckland-vpn:2041-2058`), so an invalid env value now blocks **every** command —
  including `help` and `setup`. `setup` is the documented remedy for credentials, but it cannot fix
  an invalid env value (it only prompts when `VPN_USER` is empty, `:1028`); the user must `unset`
  it. The message does say "(from the environment)", which points the right way. This mirrors the
  pre-existing config behaviour (`load_config` at `:222` was already unconditional), so it is a
  consistency improvement, not a regression introduced carelessly.
- `die()` is defined at `:190`, before the new env check at `:219` — no ordering regression.
- No die-context/test breakage: full suite 24/24.

## Q4 — Test honesty? **Both new tests are genuine; the setup test does not touch Keychain.**

- `test_env_username_rejected` (`tests/run-tests.sh:247-254`): on parent, sourcing exits 0 and prints

- `test_setup_prompt_rejects_invalid_username` (`:256-265`): on parent, `cmd_setup` *saves* the bad

  message assertion and the `[ ! -e …/config ]` assertion — both fail on parent. Honest.
- **Keychain / cmd_secret:** on the fixed code the invalid name dies at `auckland-vpn:1034-1035`,
  which is *before* `save_vpn_user_to_config` (`:1037`) and `cmd_secret` (`:1041`). Confirmed by
  probe: `cfg=[absent]`, and the output stops at the `unsupported username` error — no
  `security add-generic-password` (`:1054`) is reachable. The test does not assert this directly,
  so it is only as safe as the ordering inside `cmd_setup`; a future reorder that validates after
  saving would still pass the message check but could touch `cmd_secret`. Acceptable today,

- New tests use no privileged seams and call no privileged path; wrapper-only seam constraint

## Q5 — README accuracy vs code? **Two inaccuracies.**

`README.md:44-48`:

> The username value itself is limited to letters, digits, and `@ . _ -` — no spaces. Surrounding
> whitespace is trimmed, and one pair of matching quotes (`"..."` or `'...'`) is stripped. The same
> rule applies wherever the username comes from: the config file, the `VPN_USER` environment
> variable, and the `setup` prompt.

- **(a) Trim/quote-strip is over-generalised.** Only the config loader trims and strips quotes
  (`auckland-vpn:117-125`). The env check validates the raw value (`:219`) — no trim, no
  quote-strip. The setup prompt trims whitespace (`:1031-1032`) but does **not** strip quotes.
  Probed:
  - env `VPN_USER=' alice'` / `'alice '` / `'"alice"'` → all die `unsupported characters`;
  - setup prompt input `"alice"` → dies `unsupported username '"alice"'`.
  So a user following the README literally (`export VPN_USER='"alice"'`, expecting the quotes to
  be stripped) gets a confusing failure. The clearest split is: charset applies everywhere;
  trim+quote-strip is config-file-only; setup trims but does not strip quotes.
- **(b) Duplicates are not documented.** `#64` explicitly scopes README to "charset/quotes/**duplicates**";
  the loader rejects conflicting duplicate lines at `auckland-vpn:132-134`, but `grep -i 'duplicate|conflict' README.md`
  returns nothing. The commit body claims "README documents the value rules (#64)" — it documents
  the charset/trim/quote subset only.

## Findings (all non-security; the ingestion gate itself is sound)

1. **[MINOR] README:44-48 over-states trim/quote-strip for env and setup sources.** Verified false
   for two of the three sources. Fix: scope the sentence (config trims + strips one quote pair;
   setup trims only; env is taken verbatim apart from the charset rule).
2. **[MINOR] README does not document conflicting-duplicate rejection** (`auckland-vpn:132-134`),
   although `#64` lists "duplicates". The commit claims `#64` is covered.
3. **[MINOR] Error-message drift** between the three sites (`:130`, `:220`, `:1035`); the commit
   body's "same message" claim is inaccurate. Consider sharing the `(allowed: letters, digits, @ . _ -)`
   tail or making all three identical.
4. **[INFO] `username_is_valid ""` returns true** (`auckland-vpn:91-96`). Harmless at all current
   call sites but a latent trap; consider `[ -n "$1" ] || return 1` or a rename that makes the
   non-empty precondition explicit.
5. **[INFO] Tracker:** `#63`/`#64` are still OPEN while the commit message implies both are
   addressed. `#64` is only partially satisfied (finding 2).
6. **[INFO] Over-restriction surface:** the class rejects `+`, `\`, and other characters a
   legitimate UoA alias could in principle contain. This is the agreed `#63` spec, so noted for
   awareness only.
7. **[INFO] Stale pre-fix helper** with a bad baked username remains until `setup-sudo` is re-run;
   `%q` bake + single `--user=` argument make it non-injectable (Q1 residual).

## Verdict rationale

No path was found by which an invalid username reaches `openconnect --user` or the helper bake;
the config parse/quote/trim ordering resists smuggling; and both new tests are honest and
fail on the parent commit without touching Keychain. The blocking concerns are confined to the
commit's own documentation and messaging: README states behaviour that two of the three ingestion
points do not implement, it omits the duplicate rule `#64` named, and the three site messages (and
the commit body's "same message" claim) disagree. These are cheap, in-scope fixes that should land
before `#63`/`#64` are closed.
